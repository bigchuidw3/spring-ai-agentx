# 可观测性

v1_1 新增可观测性支持，基于 OpenTelemetry 标准，将 Agent 调用链路输出为完整的 trace 树，可对接任意支持 OTLP 协议的观测平台（Opik / Langfuse / Tempo / Jaeger 等，换后端只改 endpoint 配置）。

## 1. 基本概念

| 概念 | 含义 |
|------|------|
| **Trace** | 一次 Agent 调用的完整旅程（一条 trace = 一次 `call()`/`stream()`） |
| **Span** | 旅程中的一个节点，有名字、耗时、输入输出、父子关系，组成一棵树 |
| **ObservationRegistry** | Spring 的观测总线，由 Spring Boot 自动装配（引入依赖即有，无需手动创建） |
| **OTLP** | 观测数据的行业标准传输协议，平台通过它接收 trace |

一次调用的 span 树（trace 名为 `agentx: <问题摘要>`，观测平台中搜索 `agentx` 即得全部对话）：

```
agentx: <问题摘要>           ← 框架 TracingHook 打的：对话结构与全量内容（根）
├─ agentx.round.N.*         ←   每轮 prompt / output / tool_calls 原文
├─ chat <模型名>            ← Spring AI 打的：模型名 / token / 耗时（LLM 计量）
└─ agentx.tool.<工具名>     ← 框架 TracingHook 打的：工具参数 / 结果
```

| 想看什么 | 看哪里 |
|----------|--------|
| 用户问题 / 每轮收发原文 / 工具调用指令 / 最终答案 / token 汇总 | 根 span（`agentx: ...`）的 **Input** 标签页 |
| 某一轮的模型名 / token / 耗时 | `chat <模型名>` span（usage） |
| 工具的参数与结果 | `agentx.tool.*` 的 Input / Output 标签页 |
| 某用户 / 某会话 / 从日志反查 | Filter 按 Metadata：`userId` / `conversationId` / `otelTraceId` |

> 模型名对应的网关地址属静态配置，观测不记录（trace 记行为，配置记拓扑）。

## 2. 框架侧组件（`observability` 包）

| 组件 | 职责 |
|------|------|
| `TracingHook` | 实现 `AgentHook`，产生 `agentx.agent` 根 span 与 `agentx.tool.*` 工具 span，每轮内容记在根 span（原文不截断）；跨线程 span 携带 |
| `TracingState` | 一次调用的 span/scope 状态，经 `AgentRuntimeContext` 跨线程传递 |
| `ChatContentObservationHandler` | 给 LLM span 补 input（prompt 原文）/ output（回答原文或 tool_calls 指令） |
| `ObservabilityPredicates` | 观测范围过滤策略工厂，屏蔽 Spring AI 内部观测命名，宿主只需关心接口路径 |

数据字段（key）：

| key | 记录内容 |
|-----|---------|
| `input.value` / `output.value` | 各 span 的输入 / 输出原文（标准属性，各 span 各自持有） |
| `agentx.round.N.prompt / .output / .tool_calls` | 第 N 轮发给模型的消息 / 模型输出 / 工具调用指令（根 span） |
| `agentx.usage.prompt_tokens / .completion_tokens / .total_tokens` | 全程累计 token（根 span） |
| `agentx.total.rounds` / `agentx.final.duration_ms` | 总轮次 / 总耗时 |
| `agentx.tool.success / .duration_ms / .call_id` | 工具成败 / 耗时 / 调用标识 |
| `opik.metadata.*` | conversationId / userId / sessionId / otelTraceId（平台元数据，otelTraceId 可与日志方括号内的 traceId 互查） |

## 3. 调用方接入步骤

**1）依赖**（版本由 Spring Boot BOM 管理）：

```xml
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<dependency>
    <groupId>io.opentelemetry</groupId>
    <artifactId>opentelemetry-exporter-otlp</artifactId>
</dependency>
```

**2）application.yml**（发送目标，Boot 3.4+ 键名）：

```yaml
management:
  tracing:
    sampling:
      probability: 1.0          # 采样率，生产可调低
  otlp:
    tracing:
      endpoint: <平台 OTLP 地址，完整 URL 含 /v1/traces>
      headers:                  # 按 platform 要求配置认证
        Authorization: <api-key>
```

**3）ChatModel 构建时传入 ObservationRegistry**（注入 Spring 容器中的 Bean，激活 LLM span）：

```java
OpenAiChatModel.builder()...observationRegistry(observationRegistry).build();
```

**4）ReactAgent 构建时挂载**（核心两行）：

```java
ReactAgent.builder()
    .chatModel(chatModel)
    .observationRegistry(observationRegistry)   // LLM span
    .hooks(new TracingHook(tracer))            // Agent 结构 span
    ...
```

> Tracer 同样由 Spring Boot 自动装配，直接注入 `io.micrometer.tracing.Tracer`。

**5）观测范围（推荐，降噪）**：

```java
@Configuration
public class ObservabilityConfig {

    @Bean
    public ObservationPredicate observationPredicate() {
        return ObservabilityPredicates.agentOnly();
    }
}
```

过滤规则：只保留 Agent/LLM 链路；HTTP 入口、定时任务、Security、JDBC 等全部拦截——观测平台中只有 Agent 调用链，搜索 `agentx` 即得全部对话。

## 4. 使用与排查指引

- **日志互查**：应用日志方括号内的 traceId 即 `opik.metadata.otelTraceId`，在平台按该值检索可直接定位对应 trace
- **流式对话**：每轮内容以根 span 的 `agentx.round.*` 为准（LLM span 的流式聚合存在 Spring AI 已知缺口，框架已兜底）
- **独立 trace 的来历**：未挂 TracingHook 的 LLM 调用（如宿主自行构建的 ChatClient）会脱离主树独立成 trace；接入方式同上第 4 步
- **性能**：span 记录为微秒级内存操作，网络导出异步批量（默认 5 秒一批），不阻塞业务线程
