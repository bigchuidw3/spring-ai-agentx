# 沙箱隔离执行

## 1. 功能定位

为 Agent 的工具调用提供执行隔离：BashTool / FileSystemTools / GrepTool 的命令不直接跑在宿主机，而是在独立的沙箱环境中执行。每次 Agent 调用（call / stream / resume）对应一次沙箱的获取与释放，调用结束后工作区状态通过快照持久化，下次调用自动恢复。

不传 `sandbox(...)` 配置则完全不启用，工具保持宿主机执行。

## 2. 架构分层

```
ReactAgent
  └─ SandboxHook（订阅 BeforeCallEvent / AfterCallEvent）
       └─ SandboxManager（编排：复用 → 快照恢复 → 新建）
            ├─ SandboxBackend          容器生命周期 SPI（DockerBackend / LocalExecutionBackend）
            │     └─ ExecutionBackend  工具执行后端（随 Sandbox 实例提供）
            ├─ SnapshotStorage         tar 包存储（LocalSnapshotStorage / 自定义注入）
            └─ SnapshotMetadataStore   快照元数据（JDBC / 内存 / 自定义注入）
```

| 边界 | 职责 |
|------|------|
| **SandboxBackend** | 容器生命周期：创建 / 复用 / 快照导出 / 恢复 / 销毁 |
| **ExecutionBackend** | 工具实际执行的后端，通过 ToolContext 传给工具，工具按接口编程，不感知 docker |
| **SnapshotStorage** | tar 字节流存哪、从哪读（单机本地磁盘 / 多机注入 MinIO 等实现） |
| **SnapshotMetadataStore** | 快照元数据表（存"有没有、多大、何时"，不存文件路径） |
| **SandboxHook** | 唯一把沙箱接入 Agent 生命周期的入口 |

后端专属配置在后端实现类中设置，`SandboxConfig` 只承载通用配置。

## 3. 支撑的执行方式

| 方式 | 后端 | 场景 |
|------|------|------|
| **Docker 隔离** | `DockerBackend` | 生产推荐。命令在独立容器内执行，文件系统与宿主机隔离 |
| **本地模拟** | `LocalExecutionBackend` | 开发调试。命令在宿主机执行，路径限定在 workspace 目录内，无系统级隔离，勿执行不受信任的代码 |

两种方式对工具完全透明：工具拿到的都是 `ExecutionBackend` 接口，切换后端不改工具代码。

## 4. 快速开始

### 4.1 Docker 模式

```java
SandboxConfig sandboxConfig = SandboxConfig.builder()
        .backend(DockerBackend.builder()
                .image("ubuntu:22.04")
                .memoryMb(512)
                .cpuCount(1)
                .networkDisabled(false)
                .build())
        .isolationScope(IsolationScope.CONVERSATION)
        .snapshotDir("/data/agentx-snapshots")     // 本地快照存储必填
        .build();

ReactAgent agent = ReactAgent.builder()
        .chatModel(chatModel)
        .dataSource(dataSource)      // 可选：有则元数据写 MySQL，无则存内存
        .tools(tools)
        .sandbox(sandboxConfig)      // 传入即启用
        .build();
```

前提条件：
- 宿主机已安装 docker CLI，daemon 运行中
- 镜像已拉取（`docker pull ubuntu:22.04`），镜像内需含 `sh` / `tar` / `base64` / `ls` 等基础命令

### 4.2 Local 模式（开发调试）

```java
SandboxConfig sandboxConfig = SandboxConfig.builder()
        .backend(new LocalExecutionBackend("/data/sandbox-ws"))
        .isolationScope(IsolationScope.CONVERSATION)
        .build();
```

Local 模式文件常驻宿主机磁盘，无需快照（`supportsSnapshot() == false`），不要求配置 snapshotDir。注意：同一 backend 实例的所有会话共享同一个 workspace 目录，需要会话级隔离时为不同会话构造不同实例。

## 5. 配置详解

### 5.1 SandboxConfig（通用）

| 配置 | 默认值 | 说明 |
|------|--------|------|
| `backend` | **必填** | 显式选择执行方式：`DockerBackend.builder().build()` 或 `new LocalExecutionBackend(dir)` |
| `isolationScope` | `CONVERSATION` | 隔离级别，见第 7 节 |
| `workspaceSpec` | empty | workspace 物化规格（宿主目录 / 文件 / 内联文本 → 容器路径） |
| `strictMode` | `false` | 严格模式，见第 9 节 |
| `snapshotDir` | 条件必填 | 本地快照目录；未注入自定义 `snapshotStorage` 且后端需要快照时必填，构建期校验 |
| `snapshotStorage` | 内置 Local | 注入自定义快照存储（如 MinIO 实现），注入后无需 snapshotDir |
| `snapshotMetadataStore` | 自动选择 | 注入自定义元数据存储；不传则按是否有 DataSource 自动选 JDBC / 内存 |

### 5.2 DockerBackend（Docker 专属）

| 配置 | 默认值 | 说明 |
|------|--------|------|
| `image` | `ubuntu:22.04` | 容器镜像 |
| `workspaceRoot` | `/workspace` | 容器内工作目录 |
| `networkDisabled` | `true` | true 时以 `--network=none` 启动（Windows Docker Desktop WSL2 下曾出现 DNS 异常，如有问题可设 false） |
| `memoryMb` | `512` | 容器内存限制 |
| `cpuCount` | `1` | 容器 CPU 限制 |
| `executionTimeoutMs` | `120_000` | 单条容器命令（exec / cp / tar）超时 |

## 6. 容器生命周期

**acquire（每次调用开始，BeforeCallEvent 触发）**，按优先级三选一：

1. `findExisting`：同名容器在跑 → 直接复用（JVM 强杀残留、快照失败保留的容器都走这条路径回收）
2. 快照恢复：元数据记录存在且 tar 包存在（双重确认）→ 新建容器 + 灌入 tar + 追加物化 workspaceSpec
3. 全新创建：新建容器 + 物化 workspaceSpec

**release（每次调用结束，AfterCallEvent 触发，幂等保证恰一次）**：

1. `exportWorkspace`：容器内 workspace 导出为 tar
2. `SnapshotStorage.save`：tar 落盘（覆盖写，原子替换）
3. `SnapshotMetadataStore.save`：写元数据（唯一键 upsert）
4. `destroy`：销毁容器

**快照失败保护**：导出或落盘失败时**不销毁容器**，保留给下次 `findExisting` 复用，避免 workspace 状态丢失。

Local 模式下 export 返回 null，跳过快照环节，文件已在宿主机磁盘。

## 7. 隔离级别

| 级别 | scope key | 复用粒度 |
|------|-----------|---------|
| `CONVERSATION` | conversationId | 同会话跨调用恢复，不同会话完全隔离 |
| `USER` | userId | 同用户跨会话共享 workspace（userId 为空时退化到 conversationId） |

容器命名：`agentx-sandbox-{scopeKey}`（自动做合法性清洗）。

## 8. 快照与状态持久化

两层职责分离，tar 存储与元数据解耦：

| 层 | 内置实现 | 说明 |
|----|---------|------|
| tar 存储 | `LocalSnapshotStorage` | `{snapshotDir}/{scopeKey}.tar`，原子写入（临时文件 + ATOMIC_MOVE），snapshotId 做路径穿越校验 |
| 元数据 | `JdbcSnapshotMetadataStore` / `InMemorySnapshotMetadataStore` | `agentx_sandbox_snapshot` 表（MySQL，建表幂等）或 JVM 内存 |

关键设计：**元数据不存文件路径**，只存 scopeKey、大小、时间。文件定位由存储实现按 scopeKey 计算（本地是目录 + 文件名，MinIO 是 bucket + 对象名），因此从本地磁盘切换到对象存储时元数据表结构零改动。

每个 scopeKey 只保留最新一份快照（覆盖写），磁盘占用上限 = 会话数（USER 级别为用户数）。

**选型约定**：

| 部署形态 | tar 存储 | 元数据 |
|---------|---------|--------|
| 单节点 | 默认 LocalSnapshotStorage（snapshotDir 必填，生产请指定稳定目录） | DataSource → MySQL；无 → 内存 |
| 多节点 | 必须注入自定义 `snapshotStorage`（MinIO / OSS 等共享存储实现） | 必须共享 MySQL |

配错的典型症状（元数据查得到、存储层读不到）：表现为每次调用都"创建新容器"而非"从快照恢复"，且无报错日志。

## 9. 严格模式

默认（`strictMode = false`）失败降级：
- 构建时后端不可用（如 docker daemon 未启动）→ 打 WARN，跳过沙箱注册，工具退化为宿主机执行
- 运行中沙箱获取失败 → 打 ERROR，该次调用工具退化为宿主机执行

严格模式（`strictMode = true`）fail-closed：
- 构建时后端不可用 → 直接抛 `IllegalStateException`，Agent 构建失败
- 运行中沙箱获取失败 → 工具调用返回"沙箱不可用（严格模式），命令未执行"，**绝不降级到宿主机执行**

安全要求高的场景（执行不受信任的 LLM 生成命令）建议开启严格模式。

## 10. 多节点部署

框架只提供单节点能力，多节点由三件事组合完成：

**1. 共享 tar 存储**：实现 `SnapshotStorage` 三方法（save / load / exists）接入 MinIO 等对象存储，通过 `.snapshotStorage(...)` 注入。多节点使用本地 LocalSnapshotStorage 是配置错误，会导致快照"时灵时不灵"且无报错（见第 8 节症状）。

**2. 共享元数据库**：各节点配置同一 DataSource，元数据写同一张 MySQL 表（建表幂等，多节点同时启动安全）。

**3. 调用方加分布式锁**：沙箱的临界区是"一次 agent 调用的生命周期"（获取容器 → 执行 → 快照销毁），调用方在发起调用处用分布式锁（Redis `SET NX EX` / Redisson）串行化同 key 的调用即可，框架无需感知：

```java
if (!redisLock.tryLock("agentx:sandbox:" + lockKey)) {
    return "处理中，请稍后";
}
try {
    agent.call(query, params);
} finally {
    redisLock.unlock("agentx:sandbox:" + lockKey);
}
```

**锁 key 粒度必须与 isolationScope 一致**：`CONVERSATION` 按 conversationId 加锁，`USER` 必须按 userId 加锁（USER 级别下按 conversationId 加锁挡不住同用户多会话并发，仍会容器重名冲突）。注意分布式互斥用分布式锁，不要用 pubsub（广播通知不保证互斥）。长任务需调用方自行处理锁续期。

单节点内的并发防护（同 conversationId）由框架内 taskManager 天然承担，与调用方分布式锁不冲突。

## 11. 已知限制

- **孤儿容器**：JVM 强杀（kill -9）时 release 不触发，容器残留。同 scopeKey 的下次调用会通过 findExisting 自动复用，不同 scopeKey 的残留需手动 `docker ps` 清理
- **快照无自动清理**：会话结束快照保留（上限 = 会话数），无 TTL，长期运行按需人工或业务侧清理
- **JDBC 元数据仅 MySQL 方言**：`agentx_sandbox_snapshot` 建表语句含 AUTO_INCREMENT / ON DUPLICATE KEY / utf8mb4，其他数据库需自行扩展 `SnapshotMetadataStore`
- **容器安全加固未做**：默认 root 用户运行，未配置 read-only rootfs / cap-drop / seccomp
- **pause → resume 走快照往返**：暂停时容器销毁 + 快照，恢复时重建 + 灌 tar，每次交互有几秒开销（功能正确，性能取舍）
