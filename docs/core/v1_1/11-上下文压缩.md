# 上下文压缩

v1.0.1 的上下文压缩参考了 AgentScope 的 6 层渐进式压缩思路，并在其之上做了几点关键优化。本文档把这些差异讲清楚。

## 1. 压缩解决的是什么问题

Agent 在多轮执行里会不断追加：

- 用户消息
- 模型回复
- 工具调用参数
- 工具返回结果

如果这些内容一直原样保留，当前会话很快会出现两个问题：

1. 每轮 LLM 调用成本持续上升
2. 上下文接近模型窗口上限，甚至直接失败

因此压缩的目标不是“做长期记忆”，而是让当前会话还能继续稳定执行。

## 2. 何时进入压缩策略链

压缩不是每轮都执行完整策略链，而是先过外层门禁。

### 2.1 外层门禁

只要满足任一条件，就会进入策略链：

- `messages.size() >= msgThreshold`
- 估算 token `>= tokenThreshold`

这两个阈值是独立的：

- `msgThreshold` 控制消息条数膨胀
- `tokenThreshold` 控制内容体积膨胀

### 2.2 `lastKeep` 的含义

`lastKeep` 不是触发条件，而是保护区大小。

它的作用是：

- 最近 N 条消息不参与历史区压缩
- 让 Agent 保留一段足够新的局部上下文
- 避免刚产生的新消息立刻被当成历史压掉

## 3. 六层压缩策略总览

| 层级 | 名称 | 处理区 | 是否调 LLM | 处理目标 |
|------|------|--------|------------|----------|
| L1 | HistoricalToolList | 历史区 | 否 | 把成串连续工具消息改写成结构化清单 |
| L2 | LargeMsgOffloadWithKeep | 历史区 | 否 | 在尊重 `lastKeep` 保护区的前提下，把大块原文 offload |
| L3 | LargeMsgOffloadNoKeep | 历史区 | 否 | 处理 L2 扫不到、但仍值得 offload 的大消息 |
| L4 | HistoricalRoundSummary | 历史区 | 是 | 用 LLM 摘要较早轮次，缩短历史区 |
| L5 | CurrentRoundLargeMsg | 当前任务区 | 是 | 在当前轮继续执行前，先压掉当前轮中的单条大块内容 |
| L6 | CurrentRoundOverall | 当前任务区 | 是 | 当当前轮整体占比过高时，对当前轮整体做 LLM 压缩 |

可以看到两个明确的边界：

- **是否调 LLM**：L1-L3 不调 LLM，L4-L6 调 LLM
- **处理区**：L1-L4 处理历史区，L5-L6 处理当前任务区

## 4. 相对 AgentScope 的关键优化

AgentScope 的 6 层压缩思路本身已经非常清晰，v1.0.1 沿用了这套思路，但做了三点优化。

### 4.1 L1 抛弃 LLM 调用，改为规则替换

AgentScope 的 L1（历史工具调用压缩）即便命中也会调一次 LLM 生成摘要。但 ReAct 场景下的工具调用日志结构化非常强：

- 每次调用就是 `工具名(参数)` + `结果` 两件事
- 重复调用经常是相同工具、相同结果
- 模型摘要出来的内容，往往也就是把工具名和参数列一遍

为这种内容调一次 LLM，开销和延迟都不划算。

v1.0.1 的 L1 改为：

- 把连续工具消息按段扫描出来
- 用字符串模板生成一份工具调用清单
- 同名同参数的调用做去重
- 原文按段整体 offload，保留 uuid 链路
- 完全不调 LLM，毫秒级完成

效果上，模型仍然能看到“之前用过哪些工具、关键参数是什么”，但不需要为这种结构化信息付出 LLM 调用代价。

### 4.2 LLM 调用边界重新归类

把 6 层策略按是否调 LLM 重新归类后，开销一眼可见：

| 是否调 LLM | 层级 |
|------------|------|
| 否 | L1, L2, L3 |
| 是 | L4, L5, L6 |

这样配置和排障时更容易判断：

- “为什么压缩延迟突然变大” → 多半是触发了 L4-L6
- “为什么消息数降了但 token 没降多少” → 多半是 L1-L3 已生效但 LLM 类策略没触发
- “为什么这次压缩调了好几次 LLM” → 检查是否同一轮里 L4 之后又触发了 L5 或 L6

### 4.3 处理区边界重新归类

按处理区也做了一次归类：

| 处理区 | 层级 | 含义 |
|--------|------|------|
| 历史区 | L1, L2, L3, L4 | 压的是当前 user 之前的内容，不动当前轮 |
| 当前任务区 | L5, L6 | 压的是当前 user 之后的内容，是正在执行的任务 |

这个边界对齐到 `lastKeep` 和 `latestUserMsgIndex`，运行时能精确区分历史区和当前任务区，避免误压当前正在使用的工具结果。

## 5. 压缩后写到哪里

压缩一旦触发，当前消息视图会覆盖写到 `working_messages`。

这意味着下一轮加载历史时：

- 优先读到的就是压缩后的工作视图
- 不需要每一轮重新从原始消息链做同样的压缩

而 `original_messages` 仍然保留原始消息链，不会因为压缩而被改写成同一份内容。

## 6. 调用边界：新增 `agentx_conversation` 表

这是相对 AgentScope 的另一个关键差异。

AgentScope 只通过 sessions 持久化，调用方很难直接知道“哪几条 session 属于同一次调用”，需要自己根据时间戳或会话状态去拼。这在真实业务里非常难用：

- 想查一次调用的最终状态，得聚合多行 session
- 想统计一次调用的 token 用量，得自己累加
- 想做调用列表 / 调用历史这种最基本的前端功能，缺少直接的主键

v1.0.1 把调用边界独立成一张 `agentx_conversation` 表：

| 列 | 作用 |
|----|------|
| `conversation_id` | 会话窗口维度 |
| `session_id` | 本次调用维度 |
| `question` | 本次调用的用户输入 |
| `status` | 本次调用的状态（completed / interrupted / error） |
| `created_at` | 开局时间 |
| `completed_at` | 终态时间 |
| token 累计列 | 本次调用的 token 用量 |

调用关系仍然清晰：

- 同一 `conversation_id` 下可能有多行 `agentx_conversation`（多次调用）
- 每行 `agentx_conversation` 对应一段 `agentx_session` 的状态演进
- `agentx_session` 只负责会话消息状态，不再背负调用元信息

调用方查“我这一次调用到底发生了什么”非常直接，不用再做聚合。

## 7. 原文为什么没有丢

压缩不是直接删除原文。被移出工作视图的内容会保存在 `offload_context` 中。

`offload_context` 的职责是：

- 给每段被移出的原文分配 `uuid`
- 在工作视图里留下可回取提示
- 允许模型在需要细节时再取回原文

所以当前会话里会同时存在三种东西：

- `original_messages`：原始真相链路
- `working_messages`：压缩后的可执行视图
- `offload_context`：被替换出去但可回取的原文

## 8. `context_reload` 怎么配合使用

当模型在上下文中看到 offload 标记时，如果仅靠摘要或预览不足以回答用户，就可以调用 `context_reload`。

`context_reload` 的作用很单纯：

- 输入：offload 对应的 `uuid`
- 输出：该段原文内容

适合使用的场景：

- 用户追问之前某段被压缩掉的细节
- 模型需要核对具体工具输出或原始文本
- 预览信息不够，需要完整内容再推理一次

不适合的场景：

- 只是想“顺手全展开看看”
- 当前上下文已经足够回答用户

## 9. 压缩不是长期记忆替代品

这一点需要单独强调。

上下文压缩只负责“当前会话怎么继续跑”，它不是长期记忆替代品：

| 能力 | 解决的问题 |
|------|------------|
| 上下文压缩 | 当前会话执行时，上下文太长怎么办 |
| 长期记忆 | 跨会话有哪些知识值得保留 |

因此：

- 压缩后的 `working_messages` 只是当前工作视图
- `offload_context` 只是当前会话内部的可回取旁路
- 它们都不等于长期记忆沉淀

## 10. 常用配置项

`ContextPolicy` 里最值得先理解的是这些参数：

| 参数 | 作用 |
|------|------|
| `lastKeep` | 最近多少条消息视为保护区 |
| `msgThreshold` | 消息数达到多少时才进入压缩策略链 |
| `tokenThreshold` | 估算 token 达到多少时才进入压缩策略链 |
| `minConsecutiveToolMessages` | L1 连续工具消息阈值 |
| `largePayloadTokens` | L2/L3/L5 识别单条大消息的阈值 |
| `maxLlmCompressionCount` | L4/L5 单次最多处理多少个压缩单元 |
| `currentRoundRatio` | L6 判断当前轮占比是否过高 |

## 11. 推荐用哪个样例验证

### `CompressionLayerTest`

这个样例是 v1.0.1 下最直接的验证入口。

它的 1~6 号场景分别对应 L1-L6，重点能证明：

- 外层门禁由 `msgThreshold` / `tokenThreshold` 控制
- `lastKeep` 会影响历史区可压缩范围
- L1 不调 LLM，能在毫秒级压掉连续工具段
- 压缩后 `working_messages` 会被覆盖写
- 发生 offload 时，`offload_context` 会留下原文记录

## 12. 小结

理解 v1.0.1 压缩机制时，只记这几件事就够了：

1. 先过 `msgThreshold` / `tokenThreshold` 外层门禁
2. `lastKeep` 只负责保护尾部消息，不负责触发
3. 6 层策略按 LLM 调用分为 L1-L3（不调）和 L4-L6（调）
4. 按处理区分为 L1-L4（历史区）和 L5-L6（当前任务区）
5. L1 不调 LLM，是相对 AgentScope 的关键优化点
6. 压缩结果写入 `working_messages`，原文通过 `offload_context` + `context_reload` 保留可回取能力
7. 调用边界由独立的 `agentx_conversation` 表承担，不用调用方自己算
