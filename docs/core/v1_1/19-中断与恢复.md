# 中断与恢复

v1_1 下的暂停恢复，需要同时看两张表：

- `agentx_pause_state`：暂停快照
- `agentx_session`：当前会话状态

它们分工不同，不能混成一个概念。

## 1. 两种暂停原因

当前版本统一支持两种暂停原因：

| 暂停原因 | 枚举 | 含义 |
|----------|------|------|
| HITL 工具暂停 | `HITL_TOOL_REQUEST` | 模型命中了需要人工介入的工具调用 |
| 用户主动中断 | `USER_INTERRUPT` | 调用方主动调用 `interrupt()` 打断执行 |

无论哪一种，最终都会落成 `PauseState` 快照。

## 2. `agentx_pause_state` 和 `agentx_session` 的分工

### 2.1 `agentx_pause_state`

这张表负责保存暂停现场，也就是恢复所需的执行快照。

典型内容包括：

- `reason`
- `safe_point`
- `current_round`
- `interrupted_at`
- `snapshot_json`

而 `snapshot_json` 里又会带上完整恢复所需信息。

### 2.2 `agentx_session`

这张表负责保存当前会话消息状态，而不是暂停控制状态。

也就是说：

- 会不会继续对话，看 `agentx_session`
- 能不能从暂停点恢复，看 `agentx_pause_state`

## 3. PauseState 快照里有什么

暂停快照里最关键的字段包括：

| 字段 | 作用 |
|------|------|
| `messages` | 暂停当下的消息快照 |
| `pendingToolCalls` | 当前待处理的工具调用 |
| `safePoint` | 停在了哪个安全点 |
| `currentRound` | 当前轮次 |
| `sessionId` | 当前执行所属 session |
| `totalPromptTokens` | 已累计 prompt tokens |
| `totalCompletionTokens` | 已累计 completion tokens |
| `query` | 当前执行所对应的 query |
| `params` | 原始 `RunnableParams` |

这些信息合在一起，才足以支撑恢复。

## 4. `askUser(true)` 的默认行为

如果你只是想让 Agent 能主动向用户提问，推荐直接用：

```java
ReactAgent agent = ReactAgent.builder()
        .chatModel(chatModel)
        .stateStore(stateStore)
        .askUser(true)
        .build();
```

它的默认行为是：

- 注册内置 `ask_user` 工具
- 自动补上对应的输入型暂停拦截配置

因此 `ask_user` 的语义是：

- 用户回答就是工具结果
- 不需要把它当成“审批类工具”去执行

如果要自定义 ask-user-like 工具，应显式注册自定义工具，并通过 `PauseAdvisor.builder().askUserTool("custom_name")` 指定，而不是把它当普通审批工具处理。

## 5. HITL 恢复时的会话语义

当暂停原因是 `HITL_TOOL_REQUEST` 时，恢复会复用原 session。

这意味着：

- 恢复后仍然属于同一个 `session_id`
- 语义上是“这一轮执行还没结束，继续接着跑”
- 不会因为用户回答了一次 `ask_user`，就新开一条会话记录

## 6. 用户主动中断恢复时的会话语义

当暂停原因是 `USER_INTERRUPT` 时，需要分两种情况看。

### 6.1 只恢复，不带新 query

如果只是从原暂停点继续执行，那么还是沿着原语义恢复。

### 6.2 带新 query 恢复

如果恢复时附带新的用户 query，那么框架会新开一个 session 记录，但它仍然属于同一个 `conversationId`。

可以把它理解成：

- 会话窗口没变
- 但执行 session 换了一条新记录

所以在同一个 `conversationId` 下，你可能看到多条 `session_id` 记录串起来形成完整历史。

## 7. 安全点怎么看

当前暂停恢复还会记录 `safePoint`，用来说明中断发生在什么阶段。

常见理解方式：

- 停在 LLM 生成阶段
- 停在工具执行阶段

它的意义不在于给用户展示技术细节，而在于让恢复逻辑知道：

- 有没有待处理工具调用
- 是否需要重新接续工具执行语义

## 8. 为什么说两张表缺一不可

如果只有 `agentx_session`，你只能看到消息状态，但不知道暂停现场。

如果只有 `agentx_pause_state`，你能恢复暂停点，却没有当前会话状态持续演进的落库视图。

所以 v1_1 的正确理解应该是：

- `agentx_pause_state` 管恢复快照
- `agentx_session` 管当前会话状态
- 两者配合才构成完整的暂停恢复能力

## 9. 推荐用哪个样例验证

### `InterruptResumeSessionTest`

这个样例是 v1_1 下验证暂停恢复最直接的入口。

它能够证明：

- `USER_INTERRUPT` 和 `HITL_TOOL_REQUEST` 两条路径都能形成暂停结果
- `agentx_pause_state` 会留下暂停快照
- `agentx_session` 会持续记录当前会话状态
- `askUser(true)` 下 HITL 恢复语义是“用户回答即工具结果”
- 用户主动中断后恢复，可以在同一 `conversationId` 下形成新的 session 记录

## 10. 当前与 SubAgent 的关系

当前版本里，暂停恢复语义仍然以父 Agent 为边界。

也就是说：

- SubAgent 不能自己配 `PauseAdvisor`
- SubAgent 不能自己发 `ask_user`
- SubAgent 也不是独立的恢复边界

这也是为什么暂停恢复文档和 SubAgent 文档要分开看。

## 11. 小结

理解 v1_1 的暂停恢复，只记下面几条就够了：

- 暂停原因只有两类：`HITL_TOOL_REQUEST` 和 `USER_INTERRUPT`
- `agentx_pause_state` 保存暂停快照，`agentx_session` 保存当前会话状态
- `askUser(true)` 默认就是内置 `ask_user` 的正确配置方式
- HITL 恢复复用原 session
- 用户主动中断后若带新 query 恢复，会新开 session 记录，但仍属于同一 `conversationId`
