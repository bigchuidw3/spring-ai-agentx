# 分层记忆体系

v1_1 这一版文档先聚焦“当前会话记忆”。它负责当前会话执行期的消息状态管理，不等同于长期记忆。

## 1. 两类记忆先分开看

| 类型 | 作用 | 典型载体 |
|------|------|----------|
| 当前会话记忆 | 保障本次会话能跨轮续接、压缩、恢复 | `agentx_session` |
| 长期记忆 | 保障跨会话知识沉淀与复用 | 独立长期记忆能力 |

当前阶段的主线是当前会话记忆。长期记忆仍然存在，但不应该和 `agentx_session` 的三态模型混写。

## 2. 当前会话记忆的三种状态键

`agentx_session` 不是一张“单一历史表”，而是按 `conversation_id + state_key` 组织的当前会话状态表。

| 状态键 | 角色 | 说明 |
|--------|------|------|
| `original_messages` | 真相链路 | 保存本次会话累计形成的原始消息链，适合做完整追溯 |
| `working_messages` | 工作视图 | 保存当前工作中的可继续执行视图，可能已经压缩 |
| `offload_context` | 可回取原文 | 保存被压缩移出的原文，供 `context_reload` 按需取回 |

可以把它理解成三层分工：

- `original_messages`：保真
- `working_messages`：可继续跑
- `offload_context`：被移出但没丢

## 3. 历史加载顺序

每次新一轮对话开始时，框架会优先加载 `working_messages`；如果它为空，再回退到 `original_messages`。

这意味着：

1. 压缩后的工作视图可以跨轮延续
2. 没有发生压缩时，仍然可以用原始消息链继续对话
3. 当前会话恢复时，优先恢复“可执行视图”，而不是盲目回放全部原文

## 4. 三种状态各在什么时候写入

### 4.1 `original_messages`

终态落库时，框架只把“本次调用新增的消息”追加到 `original_messages`。它是累计追加，不做整表覆盖。

适合回答的问题：

- 这一轮到底新增了哪些消息
- 工具调用链完整长什么样
- 某段原文是否真的出现过

### 4.2 `working_messages`

`working_messages` 保存的是“当前还能继续执行的工作视图”。

它会在两类时机被覆盖写：

- 一次调用正常结束时，用本轮结束后的消息视图整体覆盖
- 压缩策略触发时，用压缩后的消息视图整体覆盖

所以它不保证保真，但保证下一轮继续执行时最合适。

### 4.3 `offload_context`

当压缩策略把某些原文移出工作视图时，这些原文不会直接丢弃，而是以带 `uuid` 的形式写入 `offload_context`。

后续如果模型发现当前上下文中的 offload 标记仍然需要展开，就可以调用 `context_reload` 按 `uuid` 取回原文。

## 5. `SystemMessage` 不进入 `agentx_session`

`SystemMessage` 属于运行时外部上下文，不属于会话消息链持久化内容。

这条规则在 v1_1 下是统一的：

- 运行时，系统提示词仍然会参与消息构建
- 持久化时，`SystemMessage` 不写入 `original_messages`
- 持久化时，`SystemMessage` 也不写入 `working_messages`

这样做的好处是：

- 会话表里只保存真实对话消息和工具消息
- 系统提示词始终由运行时重新注入，口径更一致
- 避免不同来源的 system 内容在历史中混入脏数据

## 6. 当前会话记忆与长期记忆的边界

当前会话记忆解决的是”这次会话怎么继续跑下去”，长期记忆解决的是”跨会话有哪些知识值得复用”。

不要把两者混为一谈：

| 问题 | 应该看哪里 |
|------|------------|
| 下一轮对话应该接着哪份上下文跑 | `working_messages` |
| 某条工具返回原文还在不在 | `original_messages` 或 `offload_context` |
| 某个用户跨会话偏好是否沉淀下来 | 长期记忆 |

## 7. 长期记忆

长期记忆是一套独立的跨会话知识沉淀机制。它和 `agentx_session` 三态不走同一条路径——会话记忆管”这次怎么继续跑”，长期记忆管”下次还认不认识你”。

### 7.1 启用方式

`LongTermMemoryConfig` 是唯一入口，传入即启用，不传就不启用：

```java
ReactAgent agent = ReactAgent.builder()
        .chatModel(chatModel)
        .dataSource(mysqlDataSource)
        .longTermMemory(LongTermMemoryConfig.builder()
                .vectorStore(pgVectorStore)   // 调用方预先构造的 VectorStore
                .build())
        .build();
```

VectorStore（PgVectorStore / Redis / Simple 等）由调用方构造，表名、维度、距离类型、索引类型全由调用方决定。框架只通过 `VectorStore` 接口操作，不关心底层是什么。

### 7.2 写入路径：抽取 → 去重 → 合并

每次 Agent 调用正常结束后，框架从当前 session 的 `original_messages` 中异步抽取跨会话知识：

```
SessionPersister (终态落库)
  └→ MemoryPersistor.persist(params, thisCallMessages)
       └→ [异步线程池] LongTermMemoryManager.ingestTranscript
            ├→ extractCandidates: LLM 从 transcript 抽取候选记忆（结构化输出，最多 3 条）
            ├→ for each candidate:
            │    ├→ searchSimilar: 向量检索已有相似记忆（按 userId 过滤）
            │    ├→ 命中 → mergeMemories: LLM 合并新旧 → delete 旧 + insert 合并
            │    └→ 未命中 → insertMemory: 直接新增
```

关键约束：
- 抽取源是 `original_messages`，不是压缩后的 `working_messages`
- 写入是异步的，不阻塞主流程
- 去重和检索都按 `userId` 隔离，不会跨用户混淆

### 7.3 读取路径：检索 → 注入

每次 Agent 调用开始时，框架按 `userId + query` 语义检索相关记忆，注入 system prompt：

```
LoopMessageBuilder.buildInitialMessages
  └→ MemoryInjector.buildMemorySection(params, query)
       └→ LongTermMemoryManager.searchRelevant(userId, query)
            └→ VectorStore.similaritySearch (filter: userId + type=memory)
       └→ LongTermMemoryPromptFormatter.formatSection(docs)
```

注入格式为 system prompt 末尾的 `## 长期记忆` 区块，同时提醒”以上记忆来自历史对话，可能已过时”。

### 7.4 可配置参数

| 参数 | 默认值 | 作用 |
|------|--------|------|
| `topK` | 5 | 检索注入时最多返回几条 |
| `similarityThreshold` | 0.5 | 检索注入的最低相似度门槛 |
| `dedupTopK` | 3 | 写入去重时，每条候选对比几条已有记忆 |
| `dedupThreshold` | 0.5 | 去重检索的最低相似度门槛 |
| `maxCandidatesPerCall` | 3 | 单次调用最多生成几条长期记忆 |

### 7.5 关键设计决策

- VectorStore 由调用方构造，表名、维度等全部外置
- 从 `original_messages` 抽取，不从 `working_messages`（保真相链路）
- 写入走异步线程池，不影响 Agent 响应
- 去重和检索都按 `userId` 隔离
- LLM 抽取使用 Spring AI 结构化输出，不再手写 JSON 解析

## 8. 常见理解方式

### 8.1 为什么需要同时保留 `original_messages` 和 `working_messages`

因为两者目标不同：

- `original_messages` 要尽量完整，方便追溯
- `working_messages` 要尽量适合继续执行，允许压缩

只保留一个字段，会在”保真”和”可执行”之间二选一。

### 8.2 为什么还要有 `offload_context`

因为压缩不是删除。压缩后的工作视图更短，但被替换掉的内容仍然可能有价值，所以需要一个可回取的旁路存储。

### 8.3 长期记忆为什么不从 `working_messages` 抽取

`working_messages` 可能已被压缩，丢失细节。长期记忆需要从 `original_messages` 的完整对话记录中抽取，才能拿到完整的工具结果和对话上下文。

## 9. 推荐用哪些样例验证

### `ToolCallSessionTest`

证明：

- 基础工具调用完成后，`agentx_conversation` 和 `agentx_session` 都会落库
- `original_messages` 能看到完整消息链

### `MultiTurnConversationTest`

证明：

- 同一 `conversationId` 跨多轮调用时，会复用前一轮留下的会话状态
- 当前轮能够基于上一轮的工具结果继续回答

### `MemoryTest`

证明：

- `testShortTermMemory`：当前会话记忆只在同一会话内有效，新会话回忆不到
- `testLongTermMemory`：长期记忆跨会话自动注入，新会话无需重新自我介绍

### `SubAgentSessionTest`

证明：

- SubAgent 不会自己形成独立 `agentx_session`
- 父 Agent 才是当前会话记忆的持久化边界

## 10. 小结

- 当前会话记忆 = `original_messages` + `working_messages` + `offload_context`
- 历史加载优先 `working_messages`，为空再回退 `original_messages`
- `SystemMessage` 不进入 `agentx_session`
- 长期记忆 = 从 `original_messages` 异步抽取 → 向量存储 → 跨会话注入
- 长期记忆由 `LongTermMemoryConfig` 统一入口，VectorStore 由调用方提供
