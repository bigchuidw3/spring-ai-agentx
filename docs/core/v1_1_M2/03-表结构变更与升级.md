# 表结构变更与升级指南

v1.0.1-M2 相对 v1.0.1-M1 的数据库表结构变更说明，以及从 M1 库升级到 M2 的完整操作步骤。

**重要前提**：M2 起框架**不再自动执行 ALTER 迁移**（老库不会静默升级），只保留建表幂等（表不存在时自动创建，已存在时静默跳过）。因此 **M1 老库必须按本文手动升级**，全新部署无需任何操作（启动即自动建全量表）。

---

## 1. 变更总览

框架共管理 5 张表，本次涉及 3 张：

| 表 | 变更程度 | 变更内容 |
|----|---------|---------|
| `agentx_trace` | **大改** | 新增 5 列、删除 2 列、时间列提精度（`input_data` / `output_data` 等既有列名不变） |
| `agentx_conversation` | 中改 | 新增 8 个观测汇总列 |
| `agentx_session` | 小改 | 新增 `user_id` 列 |
| `agentx_pause_state` | 无变化 | — |
| `agentx_sandbox_snapshot` | 无变化 | — |

### 1.1 agentx_trace（统一 Span 模型 + 数据隔离）

| 变更类型 | 列 | 说明 |
|---------|----|------|
| 新增 | `user_id VARCHAR(100) NULL` | 用户ID，全链路数据隔离 |
| 新增 | `span_type VARCHAR(8) NOT NULL DEFAULT 'LLM'` | Span 类型：LLM / TOOL / COMPACT，三类统一一张表 |
| 新增 | `tool_name VARCHAR(128) NULL` | 工具名（仅 TOOL） |
| 新增 | `tool_call_id VARCHAR(100) NULL` | 模型 tool_calls 的调用ID（仅 TOOL） |
| 新增 | `compact_id BIGINT NULL` | 所属 COMPACT span id（压缩摘要 LLM 挂其下），取代 M1 的 `parent_span_id`（语义收窄） |
| 删除 | `trace_id` | OTel traceId 不再落自建表（与观测平台自生成的 trace id 无对应，存了也对不上） |
| 删除 | `parent_span_id` | 由 `compact_id` 取代（删旧列 + 加新列，与改名等效） |
| 修改 | `created_at` → `TIMESTAMP(3)` | 毫秒精度，且改为 Java 侧写入事件发生时刻（原为数据库写入时刻、秒级精度） |

> `input_data` / `output_data` / `think` 等其余列名与 M1 一致，无需任何变更。

### 1.2 agentx_conversation（调用边界观测列）

一次请求一行的调用记录表，新增 8 个汇总列（终态时由框架一次写入）：

| 新增列 | 类型 | 说明 |
|-------|------|------|
| `duration_ms` | `BIGINT DEFAULT 0` | 端到端耗时（恢复场景累加） |
| `rounds` | `INT DEFAULT 0` | ReAct 轮次 |
| `tool_calls` | `INT DEFAULT 0` | 工具执行总次数 |
| `tool_failures` | `INT DEFAULT 0` | 失败工具次数 |
| `prompt_tokens` | `BIGINT DEFAULT 0` | 输入 token 累计 |
| `completion_tokens` | `BIGINT DEFAULT 0` | 输出 token 累计 |
| `total_tokens` | `BIGINT DEFAULT 0` | prompt + completion |
| `model_name` | `VARCHAR(128) NULL` | 实际使用的模型名 |

### 1.3 agentx_session（数据隔离）

| 变更类型 | 列 | 说明 |
|---------|----|------|
| 新增 | `user_id VARCHAR(100) NULL` | 用户ID，消息链按用户隔离 |

## 2. 升级方式 A：删表重建（框架自建）

**适用**：测试环境、或不在乎历史数据的场景。最简单，一条都不用 ALTER。

```sql
-- 只删有结构变化的 3 张表
DROP TABLE IF EXISTS agentx_trace;
DROP TABLE IF EXISTS agentx_conversation;
DROP TABLE IF EXISTS agentx_session;
```

然后**重启应用**，框架启动时自动按 M2 结构建表（建表幂等，重复启动安全）。

**代价（丢什么）**：

| 表 | 丢失内容 |
|----|---------|
| `agentx_trace` | 全部执行轨迹明细（每轮入参出参、工具调用原文） |
| `agentx_conversation` | 全部调用记录（问题、状态、token 汇总） |
| `agentx_session` | 全部会话消息链——**历史会话回放会失效**（对话页能看到会话列表但点开无内容） |

`agentx_pause_state`（中断现场）与 `agentx_sandbox_snapshot`（沙箱快照元数据）本次无结构变化，不删不动。若连历史中断现场也不想要，可一并 DROP，同样会自动重建。

---

## 3. 升级方式 B：ALTER 增量升级（保留数据）

逐表执行，可整段复制。所有语句在 MySQL 8.x 验证。

### 3.1 agentx_trace

```sql
-- ===== 新增列 =====
ALTER TABLE agentx_trace
    ADD COLUMN user_id      VARCHAR(100) DEFAULT NULL COMMENT '用户ID',
    ADD COLUMN span_type    VARCHAR(8)   NOT NULL DEFAULT 'LLM' COMMENT 'Span类型：LLM模型调用 | TOOL工具执行',
    ADD COLUMN tool_name    VARCHAR(128) DEFAULT NULL COMMENT '工具名（仅TOOL）',
    ADD COLUMN tool_call_id VARCHAR(100) DEFAULT NULL COMMENT '模型tool_calls的调用ID（仅TOOL）',
    ADD COLUMN compact_id   BIGINT       DEFAULT NULL COMMENT '所属COMPACT span id';

-- ===== 删除废弃列（列不存在时会报错，逐条执行、报错即跳过）=====
ALTER TABLE agentx_trace DROP COLUMN trace_id;
ALTER TABLE agentx_trace DROP COLUMN parent_span_id;

-- ===== created_at 提精度：秒级 DB 时间 → 毫秒级 Java 事件时间 =====
ALTER TABLE agentx_trace
    MODIFY COLUMN created_at TIMESTAMP(3) NULL DEFAULT NULL COMMENT '事件发生时刻（Java侧写入，毫秒精度）';

-- ===== 索引（已存在则跳过）=====
CREATE INDEX idx_agentx_trace_session ON agentx_trace (session_id);
CREATE INDEX idx_agentx_trace_conv    ON agentx_trace (conversation_id);
```

### 3.2 agentx_conversation

```sql
ALTER TABLE agentx_conversation
    ADD COLUMN duration_ms       BIGINT       DEFAULT 0  COMMENT '端到端耗时（毫秒，同session恢复场景累加）',
    ADD COLUMN rounds            INT          DEFAULT 0  COMMENT 'ReAct轮次（LLM推理轮数）',
    ADD COLUMN tool_calls        INT          DEFAULT 0  COMMENT '工具执行总次数',
    ADD COLUMN tool_failures     INT          DEFAULT 0  COMMENT '失败工具次数',
    ADD COLUMN prompt_tokens     BIGINT       DEFAULT 0  COMMENT '输入token累计',
    ADD COLUMN completion_tokens BIGINT       DEFAULT 0  COMMENT '输出token累计',
    ADD COLUMN total_tokens      BIGINT       DEFAULT 0  COMMENT 'prompt+completion',
    ADD COLUMN model_name        VARCHAR(128) DEFAULT NULL COMMENT '实际使用的模型名';
```

### 3.3 agentx_session

```sql
ALTER TABLE agentx_session
    ADD COLUMN user_id VARCHAR(100) DEFAULT NULL COMMENT '用户ID';
```

## 4. 老数据回填（可选）

ALTER 完成后，存量行的 `user_id` 为 NULL、`span_type` 为默认值 'LLM'。新代码查询按 `user_id` 过滤时老数据会被过滤掉（看不到），按需回填：

### 4.1 回填 user_id（通过 session_id 关联 conversation 表）

```sql
-- agentx_trace 回填（trace.session_id 是 BIGINT，conversation.session_id 是 VARCHAR，需 CAST）
UPDATE agentx_trace t
JOIN agentx_conversation c ON t.session_id = CAST(c.session_id AS UNSIGNED)
SET t.user_id = c.user_id
WHERE t.user_id IS NULL AND c.user_id IS NOT NULL;

-- agentx_session 回填（两侧都是 VARCHAR，直接关联）
UPDATE agentx_session s
JOIN agentx_conversation c ON s.session_id = c.session_id
SET s.user_id = c.user_id
WHERE s.user_id IS NULL AND c.user_id IS NOT NULL;
```

> 依赖 `agentx_conversation.user_id` 已有值（M1 起该列就存在且写入），且 `session_id` 唯一（表上有 `uk_conv_session` 唯一索引），关联是安全的。

### 4.2 span_type 说明

`ADD COLUMN ... DEFAULT 'LLM'` 会给全部存量行填 `'LLM'`。M1 的表里 LLM 行与工具行如何区分取决于旧版本结构；若老库无任何区分字段，存量行保持 'LLM' 即可——不影响新数据的正确性（M2 起写入的行都带准确 span_type）。

### 4.3 观测汇总列说明

conversation 新增的 8 列在存量行上为默认值 0 / NULL。是否回填由业务决定（需要历史统计口径一致时，可从 trace 表聚合回填）；不回填仅表现为历史调用的统计值显示为 0。

## 5. 升级后校验

```sql
-- 列已存在（每条应返回 1）
SELECT COUNT(*) FROM information_schema.columns
WHERE table_schema = DATABASE() AND table_name = 'agentx_trace' AND column_name = 'span_type';
SELECT COUNT(*) FROM information_schema.columns
WHERE table_schema = DATABASE() AND table_name = 'agentx_session' AND column_name = 'user_id';
SELECT COUNT(*) FROM information_schema.columns
WHERE table_schema = DATABASE() AND table_name = 'agentx_conversation' AND column_name = 'model_name';

-- 废弃列已删（每条应返回 0）
SELECT COUNT(*) FROM information_schema.columns
WHERE table_schema = DATABASE() AND table_name = 'agentx_trace' AND column_name IN ('trace_id', 'parent_span_id');

-- 发起一次对话，确认新行写入正确
SELECT span_type, tool_name, user_id, round FROM agentx_trace ORDER BY id DESC LIMIT 10;
```

## 6. 注意事项

1. **框架不做自动迁移**：M2 起代码里没有任何 ALTER，老库不升级会在写入/查询时报「Unknown column」——这是预期行为，按本文操作即可。
2. **建表幂等**：框架启动时的 CREATE TABLE 对已存在的表静默跳过，升级顺序无要求（可以先执行 ALTER 再启动新版应用）。
3. **DROP 与 ALTER 二选一**：方式 A 和方式 B 不要混用（先 ALTER 又 DROP 等于白做）。
4. **备份**：执行方式 A（DROP）前备份；方式 B 的 ALTER 全部为加列/改名/删废弃列，不破坏有效数据，但生产环境建议先在测试库演练一遍。
5. **多节点**：所有节点共用同一库，ALTER 只需执行一次；升级期间停一个节点执行完再滚动重启即可（ALTER 的 ADD COLUMN 在 MySQL 8 对大表也是秒级元数据操作）。
