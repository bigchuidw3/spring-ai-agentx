# 上下文压缩与数据隔离

上下文压缩的完整机制（6 层策略链、外层门禁、offload 回溯）见 [11-上下文压缩](../v1_1/11-上下文压缩.md)。本文讲三件事：**M2 相对 M1 的代码变更**（压缩链路全链路 userId 透传）、**L3 层处理区的语义澄清**（既有行为，此前文档描述不准确），以及**工具结果源头卸载的可配置化**（M2 新增：调用方可指定不参与卸载的工具名）。

---

## 1. M2 变更：压缩链路全链 userId 透传

### 1.1 为什么改

M1 的压缩 offload 只带 `conversationId` / `sessionId`，落库的消息没有用户维度——多用户场景下，offload 出去的原文（`agentx_session.offload_context`）无法按用户隔离查询。M2 把 `userId` 从 `RunnableParams` 一路透传到 offload 落库，与 `agentx_trace` / `agentx_session` 的数据隔离对齐。

### 1.2 变更清单（签名对照）

| 组件 | M1 签名 | M2 签名 |
|------|---------|---------|
| `OffloadStore` 接口 | `offload(conversationId, sessionId, messages)` | `offload(conversationId, sessionId, userId, messages)` |
| `OffloadStore` 单条重载 | `offload(conversationId, sessionId, message)` | `offload(conversationId, sessionId, userId, message)` |
| `ContextCompactor.compact` | `compact(messages, query, conversationId, sessionId, round, traceManager)` | `compact(messages, query, conversationId, sessionId, userId, round, traceManager)` |
| `CompressionContext` 构造 | `(messages, query, conversationId, sessionId, policy, chatModel, offloadStore)` | `(messages, query, conversationId, sessionId, userId, policy, chatModel, offloadStore)`，新增 `userId()` |
| 内置实现 | `NoOpOffloadStore` / `SessionBackedOffloadStore` | 同步改为新签名，行为不变（多透传一个 userId 落库） |

**破坏性变更**：自定义了 `OffloadStore` 实现的调用方**必须同步改签名**，否则编译不过（接口方法变了）。迁移方式：

```java
// M1：自定义实现
public class MyOffloadStore implements OffloadStore {
    @Override
    public String offload(String conversationId, long sessionId, List<Message> messages) { ... }
}

// M2：加一个 userId 参数，按需使用（如落库时写入 user_id 列）
public class MyOffloadStore implements OffloadStore {
    @Override
    public String offload(String conversationId, long sessionId, String userId, List<Message> messages) {
        // userId 即调用时 RunnableParams.userId，与 agentx_session.user_id 同源
        // 落库时带上即可实现 offload 原文的按用户隔离
        ...
    }
}
```

只通过 `ContextCompactionHook` 接入压缩的调用方**无感知**：Hook 从 `AgentRuntimeContext` 取 userId 自动传入，不需要改任何代码。

### 1.3 透传链路

```
RunnableParams.userId
  → ContextCompactionHook（取 ctx.getUserId()）
      → ContextCompactor.compact(..., userId, ...)
          → CompressionContext（持有 userId）
              → 六层策略的 offload 调用（ctx.offloadStore().offload(..., ctx.userId(), ...)）
  → ToolCallExecutor.evictIfNeeded（工具结果源头卸载，同样带 userId）
```

## 2. L3 层语义澄清（既有行为，文档修正）

此前文档（包括 README 的压缩层级表）把 L3 描述为「历史区」，不准确。L3 的实际处理区是**跨界的**：

```
消息序列：
[历史轮消息...] [user] [assistant(tool_calls)] [tool结果A] [assistant(tool_calls)] [tool结果B(最新)]
 ├─ L1/L2 在这里处理 ─┤├────────── L3 的扫描范围 ──────────┤├─ 永不触碰 ─┤
                          ↑ latestToolCallBoundary（最后一个含 tool_calls 的 assistant 之前）
```

- **扫描上界**：`CompressionContext.latestToolCallBoundary()`——最后一个含 tool_calls 的 AssistantMessage 之前
- **能卸什么**：历史区大消息 + 当前轮里已经「看过」的超长工具结果（比如当前任务执行到一半，前面几轮的工具返回特别大）
- **永不卸什么**：LLM 下一轮正在等待的最新工具结果（它之后的内容 L3 绝不碰，否则模型拿不到刚发起调用的返回）
- **触发条件**：仅在 L2 未命中时执行（外层策略链顺序保证）

### 2.1 为什么这样设计

超长工具结果（大文件内容、长命令输出）是 token 膨胀的主要来源，且大量出现在「当前任务正在执行」的过程中。如果 L3 只扫历史区（止步于 `lastKeep` / 最新 user 消息），当前轮里已经消费过的巨型工具结果要等到 L5（调 LLM 摘要）才处理，代价高。L3 用「最新工具调用边界」替代「历史区边界」，让这些已经看过的大结果走**零 LLM 成本的 offload** 路径，只留预览 + `context_reload` 回溯链路。

### 2.2 与其他层的边界关系

| 层 | 扫描上界 | 说明 |
|----|---------|------|
| L1 / L2 | `historicalScanEnd(lastKeep)` | 纯历史区，最近 lastKeep 条保护 |
| **L3** | `latestToolCallBoundary()` | 越过历史区边界，止步于最新 tool_calls |
| **L4** | `latestFinalAssistantIndex()` | 越过历史区边界，止步于最新最终回复 |
| L5 / L6 | 当前任务区 | 当前轮内的摘要压缩 |

排障提示：看到某条超长工具结果在「当前任务还没结束」时就被替换成了预览 + uuid，那是 L3 干的——原文在 `agentx_session.offload_context`，带 userId 落库，可按用户隔离查询或 `context_reload` 取回。

## 3. 工具结果源头卸载可配置化（M2 新增）

### 3.1 机制是什么

工具结果「源头卸载」是一道独立于 6 层压缩策略链的防线，发生在**工具结果刚产生时**（`ToolCallExecutor.evictIfNeeded`）：单条结果超过阈值即 offload 全文，上下文只留「首尾预览 + 占位提示」，原文进 `offload_context`，需要时用 `context_reload` 回取。

它和 6 层压缩的区别在于时机：6 层压缩在每轮推理前按策略链批量处理历史消息；源头卸载则在结果落进上下文之前先拦一道，直接针对「单条超长工具结果」这一最常见的 token 膨胀源。

M1 里这套机制是硬编码的——预览固定 1000 字符、不卸载工具名写死在 `ToolCallExecutor` 私有常量里，调用方改不了。M2 把它上移到 `ContextPolicy`，对外开放配置。

### 3.2 三个配置项

| 参数 | 类型 | 默认 | 作用 |
|------|------|------|------|
| `toolResultEvictionChars` | int | 20000 | 单条工具结果超过该字符数才触发卸载；`0` 表示禁用 |
| `toolResultEvictionPreviewChars` | int | 2000 | 卸载后首尾各保留的预览字符数（M1 硬编码 1000，M2 开放为可配置） |
| `evictionExcludedTools` | Set\<String\> | 内置 8 个 | 不参与卸载的工具名集合，**追加不覆盖**（见下） |

### 3.3 内置不卸载的工具

以下 8 个工具框架始终保留、永不卸载——它们自带分页或返回天然小，卸载反而会造成「读 → 卸载 → 回取」的死循环：

`context_reload`、`read_file`、`write_file`、`edit_file`、`list_files`、`glob_files`、`grep`、`TodoWrite`

### 3.4 怎么配置

`evictionExcludedTools` 是**追加语义**：无论调用方传什么，内置 8 个都会保留；调用方传入的集合只是额外追加，不会覆盖内置名单。

```java
import java.util.Set;

ContextPolicy policy = ContextPolicy.builder()
        .toolResultEvictionChars(20000)                             // 单条结果 > 20000 字符才卸载
        .toolResultEvictionPreviewChars(2000)                       // 卸载后首尾各留 2000 字符预览
        .evictionExcludedTools(Set.of("db_query", "large_report"))  // 追加 2 个不卸载工具
        .build();

ReactAgent agent = ReactAgent.builder()
        .chatModel(chatModel)
        .contextPolicy(policy)
        .build();
```

行为说明：

- 传 `null` 或空集合 → 等价于只保留内置 8 个（回退默认）
- 传自定义集合 → 最终生效的是「内置 8 个 ∪ 调用方集合」
- `toolResultEvictionChars(0)` → 彻底关闭源头卸载，所有工具结果原文保留（不推荐，大结果会直接顶爆上下文）

### 3.5 context_reload 分页回取

被卸载的原文不是「要么不取、要么一次全取回」——`context_reload` 本身是**分页**的：

```java
context_reload(uuid, offset, limit)
```

- 默认每页返回 8000 字符，单次最多 16000 字符（`limit` 传再大也会被截到 16000）
- 每页结果带 `nextOffset`，还有更多内容时用 `offset=nextOffset` 继续翻页，直到返回「已到末尾」
- 模型按需翻页，多数场景翻一两页就定位到答案，不必把全文全部拽回

所以整条链路的每一环都是「有界分块」，上下文不会在任何一步被突然塞进一大坨：

| 环节 | 单次上限 |
|------|---------|
| 源头卸载阈值 `toolResultEvictionChars` | 20000 字符（超过才 offload） |
| 卸载后留在上下文的预览 | 首尾各 2000 字符 |
| `context_reload` 召回一页 | 默认 8000，最大 16000 |
