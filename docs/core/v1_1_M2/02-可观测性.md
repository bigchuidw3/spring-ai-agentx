# 可观测性

基于 OpenTelemetry 标准，将 Agent 调用链路输出为完整的 trace 树，可对接任意支持 OTLP 协议的观测平台（Opik / Langfuse / Tempo / Jaeger 等，换后端只改 endpoint 配置）。同时内置自建审计存储（MySQL 三张表），记录每一轮推理、每一次工具调用的完整原文，支持按用户隔离查询。

---

## 1. 先看效果

一次 `call()` / `stream()` 调用在观测平台上的 span 树（trace 名为 `agentx: <问题摘要>`，搜索 `agentx` 即得全部对话）：

```
agentx: <问题摘要>           ← 根 span：对话结构与全量内容
├─ agentx.round.N.*         ←   每轮 prompt / output / tool_calls 原文
├─ chat <模型名>            ←   LLM span：模型名 / token / 耗时
└─ agentx.tool.<工具名>     ←   工具 span：参数 / 结果 / 成败 / 耗时
```

| 想看什么 | 看哪里 |
|----------|--------|
| 用户问题 / 每轮收发原文 / 工具调用指令 / 最终答案 / token 汇总 | 根 span 的 Input 标签页 |
| 某一轮的模型名 / token / 耗时 | `chat <模型名>` span |
| 工具的参数与结果 | `agentx.tool.*` 的 Input / Output |
| 按用户 / 会话过滤，或从日志反查 | Metadata：`userId` / `conversationId` / `otelTraceId` |

## 2. 接入步骤（从 0 到 1）

### 2.1 加依赖

```xml
<!-- 版本均由 Spring Boot BOM 管理，无需写版本号 -->
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<dependency>
    <groupId>io.opentelemetry</groupId>
    <artifactId>opentelemetry-exporter-otlp</artifactId>
</dependency>
```

引入即自动装配 `ObservationRegistry` 和 `Tracer`（Spring Boot 自动配置，无需手动创建 Bean）。

### 2.2 配置导出目标（application.yml）

```yaml
management:
  tracing:
    sampling:
      probability: 1.0          # 采样率，全量；生产可调低
  otlp:
    tracing:
      endpoint: https://www.comet.com/opik/api/v1/private/otel/v1/traces   # 平台 OTLP 地址（完整 URL）
      headers:                  # 按平台要求配置认证
        Authorization: <api-key>
        Comet-Workspace: <workspace>   # Opik 需要；其他平台按各自要求
```

### 2.3 构建 ChatModel 时传入 ObservationRegistry

激活 LLM span（模型名 / token / 耗时）。`observationRegistry` 直接从 Spring 容器注入：

```java
@Bean
public ChatModel chatModel(ObservationRegistry observationRegistry) {
    return OpenAiChatModel.builder()
            .apiKey(apiKey)
            .baseUrl(baseUrl)
            .observationRegistry(observationRegistry)   // 关键：激活 LLM span
            .build();
}
```

### 2.4 构建 ReactAgent 时挂载 TracingHook

产生 Agent 结构 span（根 span + 工具 span）。`tracer` 同样由 Spring Boot 自动装配，直接注入 `io.micrometer.tracing.Tracer`：

```java
@Bean
public ReactAgent agent(ChatModel chatModel, Tracer tracer) {
    return ReactAgent.builder()
            .chatModel(chatModel)
            .observationRegistry(observationRegistry)   // LLM span
            .hooks(new TracingHook(tracer))             // Agent 结构 span（根 + 工具）
            .dataSource(dataSource)                     // 启用自建 trace 审计存储（可选）
            .tools(...)
            .build();
}
```

核心就两行：`.observationRegistry(...)` 管 LLM span，`.hooks(new TracingHook(tracer))` 管 Agent 结构 span。

### 2.5 观测范围过滤（推荐，降噪）

不过滤的话，HTTP 入口、定时任务、JDBC 等框架观测会全部导出，观测平台里全是噪声。注册一个 `ObservationPredicate` 只保留 Agent/LLM 链路：

```java
@Configuration
public class ObservabilityConfig {

    @Bean
    public ObservationPredicate observationPredicate() {
        return ObservabilityPredicates.agentOnly();   // 框架提供的过滤策略
    }
}
```

过滤规则：只保留 `spring_ai` / `gen_ai` 前缀的 LLM 观测；其余（HTTP 入口、定时任务、Security、JDBC、Advisor 中间层）全部拦截。效果：观测平台中只有 Agent 调用链。

### 2.6 调用时传 userId / conversationId

trace 的 Metadata 和自建审计表都按这些标识区分数据：

```java
RunnableParams params = RunnableParams.builder()
        .conversationId("conv_001")   // 会话窗口标识
        .userId("42")                 // 用户标识：写入 trace 元数据 + 自建三张表，实现数据隔离
        .build();

String answer = agent.call("帮我分析这个文件", params);
```

传了 `userId` 后，观测平台按 `opik.metadata.userId` 过滤即可只看该用户的链路。

## 3. 完整接入示例

```java
@Configuration
public class AgentObservabilityConfig {

    /** 降噪：只保留 Agent/LLM 观测 */
    @Bean
    public ObservationPredicate observationPredicate() {
        return ObservabilityPredicates.agentOnly();
    }

    @Bean
    public ChatModel chatModel(ObservationRegistry registry) {
        return OpenAiChatModel.builder()
                .apiKey(System.getenv("OPENAI_API_KEY"))
                .observationRegistry(registry)
                .build();
    }

    @Bean
    public ReactAgent agent(ChatModel chatModel,
                            ObservationRegistry registry,
                            Tracer tracer,
                            DataSource dataSource) {
        return ReactAgent.builder()
                .chatModel(chatModel)
                .observationRegistry(registry)
                .hooks(new TracingHook(tracer))
                .dataSource(dataSource)          // 启用自建审计存储（agentx_trace 等三张表自动建）
                .tools(BashTool.create())
                .build();
    }
}
```

调用：

```java
RunnableParams params = RunnableParams.builder()
        .conversationId(conversationId)
        .userId(userId)
        .build();
Flux<AgentStreamEvent> stream = agent.streamForResult(question, params);
```

## 4. 自建审计存储（MySQL）

传 `dataSource` 后，框架自动建三张表（幂等），无需调用方执行 DDL。区别于观测平台的「链路视图」，这三张表是**可 SQL 查询的原始数据**，适合做统计看板、调用列表、历史回放。

### 4.1 三张表

| 表 | 粒度 | 内容 |
|----|------|------|
| `agentx_conversation` | 一次请求一行 | question、status、耗时、轮次、工具次数、token、模型名（终态汇总写入） |
| `agentx_trace` | 一个 Span 一行 | 统一 Span 模型：LLM / TOOL / COMPACT 三类，含完整入参出参原文 |
| `agentx_session` | 一条消息一行 | 会话消息链，按 state_key 分态（original / working / offload） |

三张表都有 `user_id` 列（从 `RunnableParams.userId` 透传写入），按用户隔离查询：

```sql
-- 某用户的工具使用统计
SELECT tool_name, COUNT(*) FROM agentx_trace
WHERE user_id = '42' AND span_type = 'TOOL'
GROUP BY tool_name;

-- 某用户的调用列表
SELECT session_id, question, status, total_tokens, duration_ms
FROM agentx_conversation
WHERE user_id = '42'
ORDER BY id DESC;

-- 某次调用的完整执行序列（雪花 ID 单调，按 id 排序即执行顺序）
SELECT * FROM agentx_trace WHERE session_id = 123 AND user_id = '42' ORDER BY id;
```

### 4.2 统一 Span 模型（agentx_trace）

| span_type | 含义 | 关键字段 |
|-----------|------|---------|
| `LLM` | 一次模型调用 | `input_data`（完整请求 JSON）/ `output_data`（回答或 tool_calls）/ `think`（思考）/ token / 耗时 |
| `TOOL` | 一次工具执行 | `tool_name` / `tool_call_id` / `input_data`（入参）/ `output_data`（结果） |
| `COMPACT` | 一次上下文压缩 | `tool_name`（策略名）/ `output_data`（前后 token 等详情）/ `compact_id` |

`round` 记录 ReAct 轮次；工具 Span 的 round 为发起该调用的 LLM 轮次——`ORDER BY id` 即可线性还原 `LLM 轮 → 工具 → LLM 轮` 的执行序列。失败的调用只有这张表有记录（失败轮不产生会话消息）。

### 4.3 记录时机的选择

自建表在**终态时批量落库**（一次调用的新增消息一次性写入，ReAct 循环中不产生 DB I/O），`created_at` 记录的是事件发生时刻（Java 侧捕获）而非入库时刻。写入失败仅打 WARN 日志，不影响 Agent 主流程。

## 5. Span 数据字段速查

| key | 记录内容 |
|-----|---------|
| `input.value` / `output.value` | 各 span 的输入 / 输出原文（标准属性） |
| `agentx.round.N.prompt / .output / .tool_calls` | 第 N 轮发给模型的消息 / 模型输出 / 工具调用指令（根 span） |
| `agentx.usage.prompt_tokens / .completion_tokens / .total_tokens` | 全程累计 token（根 span） |
| `agentx.total.rounds` / `agentx.final.duration_ms` | 总轮次 / 总耗时（根 span） |
| `agentx.tool.success / .duration_ms / .call_id` | 工具成败 / 耗时 / 调用标识 |
| `opik.metadata.userId / .conversationId / .sessionId / .otelTraceId` | 平台元数据（按用户过滤、与日志互查） |

---

## 6. 框架侧组件

| 组件 | 职责 |
|------|------|
| `TracingHook` | 实现 `AgentHook`，产生根 span 与工具 span，每轮原文记在根 span（不截断）；跨线程 span 携带 |
| `TracingState` | 一次调用的 span/scope 状态，经 `AgentRuntimeContext` 跨线程传递 |
| `ChatContentObservationHandler` | 给 LLM span 补 input（prompt 原文）/ output（回答或 tool_calls 指令） |
| `ObservabilityPredicates` | 观测范围过滤策略工厂（`agentOnly()`） |

---

## 7. 排查指引

**日志与 trace 互查**：应用日志方括号内的 traceId 即 `opik.metadata.otelTraceId`，在平台按该值检索直接定位对应 trace。

**出现了独立的 trace**：未挂 `TracingHook` 的 LLM 调用（如调用方自行构建的 ChatClient）会脱离主树独立成 trace。接入方式见 2.4。

**流式对话内容去哪看**：以根 span 的 `agentx.round.*` 为准。LLM span 的流式聚合存在 Spring AI 已知缺口，框架已兜底。

**平台收不到 trace（HTTP 409 等）**：多为 OTel traceId 格式与平台要求不符（部分平台要求合法 UUID）。可自定义 `SdkTracerProvider` Bean，用 UUID 版 `IdGenerator` 覆盖默认的随机 16 字节生成。

**性能**：span 记录为微秒级内存操作，网络导出异步批量（默认 5 秒一批），不阻塞业务线程。
